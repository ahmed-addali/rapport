\section{Introduction}
Le passage de la plateforme \textit{Guidni} d'un environnement de développement local à un environnement de production exige une infrastructure robuste, hautement disponible et évolutive. Dans un premier temps, afin de minimiser l'empreinte matérielle et réduire les coûts initiaux d'hébergement sur le Serveur Privé Virtuel (VPS), le système s'appuie sur des API d'inférence cloud externes (telles que Groq, Anthropic ou Google GenAI). Néanmoins, l'architecture a été rigoureusement conçue pour permettre, à court ou moyen terme, une transition fluide vers un modèle de langage (LLM) open-source hébergé localement (ex. Qwen, Llama) sur un serveur VPS dédié équipé de GPU, garantissant ainsi une totale souveraineté des données. Ce chapitre détaille la topologie de déploiement des microservices, la stratégie d'orchestration par conteneurs et les mécanismes de routage sécurisés mis en oeuvre.


\section{Topologie d'Isolation des Microservices}
Afin de garantir la tolérance aux pannes et une segmentation réseau stricte, chaque composant applicatif est isolé dans son propre conteneur Docker indépendant. Ces conteneurs communiquent dynamiquement au sein d'un réseau virtuel privé de type \textit{bridge}, empêchant ainsi l'exposition directe des ports de la base de données ou des API internes sur l'internet public.

La répartition physique des composants applicatifs ainsi que l'isolation des différents segments réseau de la plateforme sont illustrées en détail dans le diagramme de déploiement de la Figure~\ref{fig:diagramme_deploiement}. Comme on peut le constater, les bases de données relationnelles et vectorielles possèdent une étanchéité totale vis-à-vis de l'extérieur.

\begin{itemize}
    \item \textbf{Couche Proxy Inverse (Nginx) :} Connectée directement aux interfaces réseau de l'hôte sur les ports 80 (HTTP) et 443 (HTTPS). Elle gère la terminaison SSL via des certificats automatisés Let's Encrypt et redirige le trafic utilisateur vers la couche de présentation.
    \item \textbf{Couche Présentation (Next.js) :} S'exécute dans un conteneur configuré sur le port interne 3000. Elle prend en charge le rendu côté serveur (SSR), les interactions CRUD standards et l'authentification via Better-Auth.
    \item \textbf{Agent Planificateur AI (FastAPI) :} Fonctionne de manière asynchrone sur le port 8000. Il coordonne les workflows multi-agents avec LangGraph et effectue des recherches vectorielles rapides sur le serveur Qdrant local pour enrichir le contexte du RAG avant de transmettre les requêtes vers les services d'API externes.
    \item \textbf{Moteur de Recommandation (FastAPI) :} Opère sur le port 8001 pour traiter les calculs algorithmiques synchrones et vectoriels à l'aide de NumPy.
    \item \textbf{Base de Données Vectorielle (Qdrant) :} Isolé dans son propre conteneur, ce moteur gère le stockage et la recherche de similarité des plongements sémantiques (\textit{embeddings}) nécessaires au fonctionnement de l'agent intelligent.
    \item \textbf{Couche de Persistance Relationnelle (PostgreSQL) :} Isolée rigoureusement au sein du réseau Docker interne sur le port 5432, sans aucun mappage de port vers l'extérieur de la machine hôte.
\end{itemize}


\section{Pipeline de Déploiement Séquentiel}
La mise en oeuvre pratique et le déploiement opérationnel suivent un protocole strict et séquencé afin de garantir des migrations de base de données sans perte de données et une continuité de service :

\begin{enumerate}
    \item \textbf{Préparation de l'environnement :} Les mises à jour du système sont appliquées sur le VPS, puis les démons Docker et Nginx sont initialisés. Les identifiants sensibles (clés d'API, mots de passe de base de données) sont structurés de manière isolée dans un fichier masqué \texttt{.env}.
    \item \textbf{Compilation des images :} Les images Docker sont construites à partir des sources. Les composants Next.js sont optimisés pour la production, et le client Prisma génère ses types localement avant de finaliser la couche d'exécution.
    \item \textbf{Initialisation des conteneurs :} L'ensemble de l'infrastructure est démarré en arrière-plan via la commande :
    \begin{verbatim}
    docker-compose up --build -d
    \end{verbatim}
    \item \textbf{Migration du schéma de base de données :} Les transitions structurelles de la base de données relationnelle sont appliquées de manière sécurisée sans interrompre le trafic réseau existant :
    \begin{verbatim}
    docker exec -it guidni-next npx prisma migrate deploy
    \end{verbatim}
    \item \textbf{Configuration du routage et chiffrement :} Nginx est configuré pour rediriger le trafic HTTP externe vers le port conteneurisé 3000, puis Certbot valide les défis ACME afin d'obtenir et d'installer les certificats TLS SHA-256.
\end{enumerate}

\section{Conclusion}
Le choix d'une architecture découplée avec un conteneur dédié par service offre à la plateforme \textit{Guidni} une 
flexibilité d'évolution maximale. Cette configuration minimise les coûts opérationnels au lancement grâce à l'usage 
ciblé des API de LLM distantes, tout en maintenant localement l'infrastructure vectorielle Qdrant indispensable à 
l'expérience temps réel. Elle pose également les fondations techniques indispensables pour migrer ultérieurement 
l'agent planificateur vers un serveur d'inférence LLM local auto-hébergé, ou pour externaliser la persistance vers 
un service managé distribué au fur et à mesure de la croissance du nombre de voyageurs sur la plateforme.
